# 2026-11-05 — RSSI on both legs, and the 5G SNR that was never filled

**Status:** deployed and verified live on `greenpacket` (5G-NSA up: B3 + n41).
**Scope:** RG520N-EB (GreenPacket O5A Pro), `LE.UM.6.2.3.r1-03100-SDX65.0`.
**Reference:** [`carrier-aggregation.md`](../reference/carrier-aggregation.md),
[`radio-information.md`](../reference/radio-information.md),
[`platform-matrix.md`](../reference/platform-matrix.md).

## What the owner asked

> "on this page [the vendor UI] we have both RSSI for 5G and 4G, but on qmanager we
> don't have that, add its support on dashboard and cellular"

and then, while that was in flight:

> "also on http://192.168.0.1:8080/cellular/, 5G SNR is not shown"

Two defects, one root cause each, and the second one is the same class as
[`2026-11-05-signal-metric-provenance.md`](./2026-11-05-signal-metric-provenance.md):
a field that exists on the modem but was never published.

## What was measured

### The NR SCC line carries no metrics at all on this firmware

Captured live with the extended-reporting toggle **on**:

```
+QCAINFO: "PCC",1850,100,"LTE BAND 3",1,420,-70,-13,-36,1
+QCAINFO: "SCC",509070,7,"NR5G BAND 41",776          <- PCI and nothing else
```

`docs/reference/poller-cpu-profile.md:118-119` records the O5A answering
`"NR5G BAND 41",47,-67,-11,2529` with `=1`. **It does not today.** The extended
NR fields are not coming back, so an NR carrier built from QCAINFO alone has
RSRP, RSRQ, SNR and RSSI all null — which is exactly "5G SNR is not shown".

The values do exist, three sources agreeing on one poll of n41:

| Source | RSRP | RSRQ | SINR | RSSI |
| --- | --- | --- | --- | --- |
| `AT+QENG="servingcell"` → `NR5G-NSA` line | −77 | −11 | 17 | — (no field) |
| PHY/QMI read (`.phy.nr`) | −77 | −11 | 17 | — |
| modemd (`NR_rsrp` / `NR_rsrq` / `NR_sinr` / `NR_rssi`) | −77 | −11 | 18 | **−64** |

So for **NR** the QENG SINR is trustworthy — the opposite of LTE, where field 17
disagrees with `AT+QSINR` by ~10 dB. That asymmetry is why the NR fill includes
`sinr` while the LTE SCC fill deliberately does not.

### There is no AT source for NR RSSI

Neither command has the field: QCAINFO's NR line stops at the PCI, and the
`NR5G-NSA` line is `MCC,MNC,PCI,RSRP,SINR,RSRQ,ARFCN,band,bw,scs`. The vendor
stack's own metrics daemon takes it from modemd, with the comment
*"no QMI source for NR RSSI on this fw"* (`greenpacket deploy/gp-metricsd.awk:407`).
modemd is therefore the only source, and it reports `NR_rssi: "-64"`.

**LTE RSSI needed nothing**: `AT+QCAINFO` field 9 has carried it every cycle all
along — it was only the 5G card and the per-carrier rows that lacked one.

## What was built

### Backend (`scripts/`, no app-layer exception needed)

| File | Change |
| --- | --- |
| `usr/lib/qmanager/phy_metrics.sh` | new `qm_phy_nr_rssi` — one `ubus call modemd status`, value pulled out with shell parameter expansion (jq only as a fallback) |
| `usr/bin/qmanager_poller` | `nr_rssi_read()` runs once per cycle **only when `network_type` is 5G-NSA or 5G-SA**, so an LTE-only link pays nothing; `nr.rssi` is published in the status cache |
| `usr/lib/qmanager/parse_at.sh` | `parse_ca_info` fills the serving NR carrier's `sinr` (from QENG) and `rssi` (from modemd), matched on ARFCN; `nr_rssi` added to `parse_serving_cell`'s reset list |

### App layer (AGENTS.md exception 11)

| File | Change |
| --- | --- |
| `components/dashboard/signal-rows.ts` | the 5G card gets an RSSI row, barless and untinted exactly like the 4G card's |
| `lib/radio-info.ts` | RSSI is emitted for NR carriers too (it was gated on `technology === "LTE"`) |
| `components/cellular/radio/active-bands-card.tsx` | **removed the `.filter(m => m.id !== "rssi")`** that an earlier direct request had put there — see below |
| `types/modem-status.ts` | `NrStatus.rssi` |

The cellular card already rendered a barless metric correctly (a caption in the
meter lane, no track, no quality word), so restoring RSSI was deleting a filter,
not teaching the cell a new form. The earlier removal's objection — "no 0-100
scale to plot, reads as an afterthought next to three real bars" — is exactly what
the `barless` branch exists to avoid, and the comment in the file now says so, so
the next agent does not re-add the filter.

## Benchmark (AGENTS.md rule 1a — this change adds work to the hot path)

Same unit, same harness (`/tmp/qm_measure.sh`, total CPU including reaped
children), 120 s windows, 5G-NSA up throughout, poller restarted before each
window so each measures a fresh process.

| Build | Window | CPU | Share of one core | Forks/s |
| --- | --- | --- | --- | --- |
| Before (no NR RSSI read) | 120 s | 8,600 ms | 7.2 % | 68 |
| Cut 1 — one longest-match strip on the whole reply | 120 s | 10,120 ms | 8.4 % | 76 |
| Cut 2 — `printf \| jq -r` | 120 s | 9,660 ms | 8.1 % | 63 |
| **Shipped — line-by-line walk, no jq** | per call | **10.5 ms** | **~0.26 %** at the ~4 s cycle | 0 extra |

The window-level numbers could not resolve the difference (fork rates 63–76/s
across the three windows, ambient load moving), so the decision was made on
**per-call cost**, measured directly with 20 iterations each:

| Shape | Cost per call | Why |
| --- | --- | --- |
| `qm_phy_modemd` (existing helper) | 103 ms | capture file + timeout wrapper + full jq projection |
| `${out##*'"NR_rssi": "'}` on the whole 2.2 KB reply | **80 ms** | busybox ash retries a leading-`*` longest match at every position — O(n²) in the reply length |
| `printf \| jq -r '.NR_rssi'` | ~15 ms | one fork per side of the pipe |
| **walk the reply line by line** | **10.5 ms** | the daemon prints one key per line, so each match runs on ~30 bytes and needs no process; a here-doc under 4 KB does not fork |

That last row is what shipped: one `ubus call` (~5 ms) plus a shell walk, jq kept
only as a fallback if the reply shape changes. **The 80 ms figure is the useful
one to remember** — it is the shape that looks cheapest and is the most
expensive, and it was in a deployed build for twenty minutes.

## Edge cases (AGENTS.md rule 2)

| Edge case | How it was exercised | Observed |
| --- | --- | --- |
| No NR leg (LTE-only) | gate on `network_type` | `nr_rssi` empty, no modemd call at all, `nr.rssi: null` |
| NR leg drops mid-run | live: NR left the air at 07:18 UTC | `nr.rssi` → null; no stale value carried |
| modemd absent / not answering | `qm_phy_nr_rssi` returns 2/3 | empty value → `null`, never 0 |
| Non-numeric answer (`n/a`) | fixture | rejected by the charset guard |
| Reply spacing changes | fixture with no space after the colon | shell path yields nothing, jq fallback takes over |
| `NR_rssi` vs `rssi` vs `sss_rssi` | fixture containing all three keys | only `NR_rssi` matches — the extractor anchors on the quoted key and the colon |
| NR SCC line with no metrics | live (always) | RSRP/RSRQ/SNR/RSSI all filled; before, all four were dashes |
| ARFCN mismatch | fixture with a non-serving NR carrier | no fill — a non-serving NR carrier stays null rather than borrowing the serving cell's readings |
| Live end-to-end | device, both surfaces | dashboard 5G card `RSRP −77 / RSRQ −11 / SINR 17 / RSSI −64 dBm`; /cellular `ANCHOR NR n41 … SNR 18 dB, RSSI −64 dBm` and `PCC LTE B3 … RSSI −38 dBm` |

## The deploy trap this hit (record it)

The first deploy of the changed poller **broke the service**: I shipped
`qmanager_poller` *after* running `qm_pathfix.sh`, so the new file kept the
upstream `. /usr/lib/qmanager/parse_at.sh` path, failed to source it, and exited 1
— `systemctl status` showed `status=1/FAILURE` with no log line, and after three
such restarts systemd's start-rate limiter refused further starts
(`Job for qmanager-poller.service failed` with the status timestamp frozen).
Recovery was `systemctl reset-failed qmanager-poller` + start, after re-running
`qm_pathfix.sh`.

`AGENTS.md` already says `qm_pathfix.sh` must be re-run after **every** redeploy
of the backend; this is what it looks like when it is not. Order matters:
ship → pathfix → restart. And when a unit "fails to start" with no log output,
read `systemctl status` for the exit code and `reset-failed` before assuming the
code is broken.

## Still open

- **The extended NR QCAINFO fields did not appear**, so the NR carrier's readings
  come from QENG/modemd rather than from the CA reply. If a firmware update makes
  `=1` report them again, `parse_ca_info` will use them and the fill becomes a
  no-op — no change needed, but re-measure rather than assume.
- **RSSI is per serving cell.** A second NR carrier (n41+n41) will show null RSSI:
  modemd publishes one `NR_rssi`, for the leg it is serving. Do not spread it
  across carriers.
- The swap baseline moved by ~7.5 MB during the deploy (see
  `2026-10-25-swap-growth.md`); this is expected on a swappiness-100 box and is
  not caused by this change.
